# Architecture

## 1. Overview

The `arc-aws-observability-postgres-dbre` project is a production-inspired portfolio environment designed to demonstrate AWS observability, Infrastructure as Code, containerized PostgreSQL administration, operational troubleshooting, backup and recovery, and CI/CD validation.

The project consists of three primary architectural areas:

1. AWS observability infrastructure managed with Terraform
2. A local containerized PostgreSQL platform managed with Docker Compose
3. GitHub Actions workflows used to validate infrastructure and container configuration

The project emphasizes operational practices associated with Cloud Engineering, Database Reliability Engineering (DBRE), Site Reliability Engineering (SRE), and cloud database administration.

## 3. Infrastructure as Code Architecture

AWS infrastructure is defined using Terraform under the `terraform/` directory.

The configuration manages resource creation, configuration, tagging, and teardown. Terraform also provides a repeatable mechanism for rebuilding the AWS environment after it has been destroyed.

The Terraform configuration includes:

* AWS provider configuration
* Environment variables
* Project naming standards
* Default resource tagging
* AWS identity and region discovery
* SNS alerting
* CloudWatch monitoring
* CloudTrail auditing
* S3 log storage and protection
* Infrastructure outputs

Provider-level default tags apply consistent metadata to supported AWS resources.

The tagging model includes:

* `Project`
* `Environment`
* `Owner`
* `ManagedBy`
* `Purpose`

This provides consistent identification of project infrastructure and demonstrates basic resource-governance practices.

## 4. AWS Observability Architecture

### 4.1 CloudWatch Dashboard

Terraform creates a CloudWatch dashboard that provides a centralized observability view for the project.

The current dashboard includes:

* Project identification
* AWS estimated-charge monitoring

The dashboard establishes an observability foundation that can be expanded with additional infrastructure and database metrics in future versions.

### 4.2 CloudWatch Alarm

The project implements a CloudWatch alarm using the AWS Billing `EstimatedCharges` metric.

The alarm evaluates estimated AWS charges against a configured test threshold.

The alert flow is:

```text
AWS Billing Metric
       |
       v
CloudWatch Alarm
       |
       v
    SNS Topic
       |
       v
Email Subscription
       |
       v
Administrator Notification
```

This demonstrates the complete monitoring-to-notification path rather than creating an alarm without an operational notification mechanism.

The billing alarm is intentionally used as a low-complexity test alarm for validating the observability and notification architecture.

---

## 5. SNS Alerting Architecture

Terraform creates an Amazon SNS topic for operational alerts.

An email subscription is associated with the topic. After deployment, the subscription must be confirmed through the email generated by AWS before notifications can be delivered.

The SNS topic is connected to the CloudWatch billing alarm through the alarm's action configuration.

This creates the following operational pattern:

```text
Metric
  |
  v
Alarm
  |
  v
SNS
  |
  v
Email
```

The same pattern can later be extended to database, infrastructure, application, or availability alarms.

## 6. CloudTrail Audit Architecture

AWS CloudTrail provides API and account activity auditing for the project.

Terraform configures the trail as:

* Enabled for logging
* Multi-region
* Inclusive of global service events
* Integrated with dedicated S3 log storage

The logging path is:

```text
AWS API Activity
       |
       v
   CloudTrail
       |
       v
Dedicated S3 Bucket
```

CloudTrail provides an audit trail that can be used during operational investigation, infrastructure troubleshooting, and security review.

---

## 7. CloudTrail S3 Log Protection

A dedicated S3 bucket stores CloudTrail logs.

The bucket includes several protection mechanisms.

### Server-Side Encryption

S3 server-side encryption using AES-256 protects CloudTrail log objects at rest.

### Versioning

S3 bucket versioning is enabled.

Versioning protects against accidental replacement or deletion of log objects while also introducing the need to manage noncurrent object versions.

### Public Access Protection

The S3 public-access configuration enables:

* Block public ACLs
* Ignore public ACLs
* Block public policies
* Restrict public buckets

CloudTrail logs are therefore not intended for public access.

### CloudTrail Bucket Policy

The bucket policy permits the CloudTrail service to:

* Check the bucket ACL
* Write CloudTrail log objects

Access is scoped to the CloudTrail service and the AWS account log path.

### Lifecycle Retention

The project defines a lifecycle policy for CloudTrail log storage.

The current portfolio retention strategy is:

* Current CloudTrail objects expire after 90 days
* Noncurrent versions expire after 30 days
* Incomplete multipart uploads are removed after 7 days

These values are intended for the portfolio environment and should not be interpreted as a universal production or regulatory retention standard.

Production retention requirements should instead be determined by organizational, security, audit, compliance, and recovery requirements.

## 8. Docker PostgreSQL Architecture

The database portion of the project runs locally using Docker Compose.

The environment contains two primary services:

```text

     |

     |                     |
     v                     v

dbre-postgres         dbre-pgadmin
     ^                     |
     |_____________________|
```

Docker's internal network allows pgAdmin to connect to PostgreSQL using the PostgreSQL service name rather than the host's loopback address.

## 9. PostgreSQL Service

The PostgreSQL container provides the database platform for DBRE exercises.

The implementation includes:

* PostgreSQL 16
* Dedicated application database
* Dedicated application user
* Persistent Docker storage
* Initialization SQL
* Container health monitoring
* Host port exposure for database access

The database used by the project is:

```text
appdb
```

The application user is:

```text
appuser
```

Credentials are supplied through the local Docker environment and should not be committed to source control.

---

## 10. PostgreSQL Initialization

The `docker/init.sql` file initializes database objects when a new PostgreSQL data volume is created.

The initialization process creates an application schema and health-check table and inserts an initial health record.

This provides a known database object that can be used for:

* deployment validation
* SQL testing
* monitoring exercises
* backup validation
* restore validation
* troubleshooting exercises

---

## 11. Persistent Storage

PostgreSQL uses a Docker named volume for database persistence.

The volume separates database storage from the lifecycle of the PostgreSQL container.

As a result, stopping or recreating a container does not automatically remove the database files.

This allows the project to demonstrate the distinction between:

```text
Container Lifecycle
```

and:

```text
Database Storage Lifecycle
```

pgAdmin also uses persistent storage for its configuration.

Removing Docker volumes is therefore treated as a destructive operation and should only be performed when persistent project data is no longer required.

---

## 12. PostgreSQL Health Monitoring

The PostgreSQL container includes a health check based on PostgreSQL readiness.

Container health can be inspected using:

```text
docker ps
```

A functioning database container should eventually report:

```text
healthy
```

The health check provides a basic container-level database availability signal and is also used as a dependency for the pgAdmin service.

## 13. pgAdmin Architecture

pgAdmin provides browser-based PostgreSQL administration for the project.

The pgAdmin container communicates with PostgreSQL through the Docker network.

The logical connection is:

```text
Web Browser
     |
     v
localhost:8080
     |
     v
pgAdmin Container
     |
     v
Docker Network
     |
     v

```

This provides a graphical administration interface while PostgreSQL command-line tools remain available for operational validation and troubleshooting.

## 14. Backup and Recovery Architecture

PostgreSQL backup and restore operations are automated using PowerShell scripts under the `scripts/` directory.

The backup workflow is:

```text
PowerShell Backup Script
          |
          v
        pg_dump
          |
          v
PostgreSQL Container
          |
          v
Temporary SQL Dump
          |
          v
      docker cp
          |
          v
Host Backup Directory
```

Backup files are written under:

```text
backups/postgres/
```

Backup files are local operational artifacts and are not intended to be committed to the public repository.

The restore workflow reverses the process:

```text
Host SQL Backup
       |
       v
   docker cp
       |
       v
PostgreSQL Container
       |
       v
      psql
       |
       v
Restored Database Objects
```

The project includes an operational recovery exercise in which database data was modified or removed, restored from backup, and subsequently validated.

This demonstrates recovery validation rather than backup creation alone.

## 15. Operational Troubleshooting

The project uses several layers of operational troubleshooting.

### Container Layer

Docker commands provide visibility into:

* container state
* container health
* startup failures
* runtime logs
* stopped containers

### PostgreSQL Layer

PostgreSQL queries provide visibility into:

* database availability
* PostgreSQL version
* current database
* database time
* health-check data
* active database sessions

The PostgreSQL `pg_stat_activity` view is used to inspect database activity.

### AWS Layer

AWS troubleshooting sources include:

* CloudWatch dashboards
* CloudWatch alarms
* SNS notifications
* CloudTrail audit records

Together these provide multiple observability points rather than relying on a single monitoring source.

## 16. CI/CD Validation Architecture

GitHub Actions provides automated configuration validation.

Two workflows are currently implemented.

### Terraform Validation

The Terraform workflow performs automated checks that include:

* Terraform formatting verification
* Terraform initialization
* Terraform configuration validation

### Docker Validation

The Docker workflow validates the Docker Compose configuration.

The CI flow is:

```text
Git Push / Pull Request
          |
          v
     GitHub Actions
       /        \
      v          v
 Terraform     Docker
 Validation   Validation
```

These workflows provide automated configuration-quality gates.

The current workflows validate configuration. They do not represent a fully automated production Terraform deployment pipeline and do not automatically apply infrastructure changes.

---

## 17. Security and Repository Controls

The repository uses `.gitignore` rules to prevent local or sensitive operational artifacts from being intentionally committed.

Examples include:

* Terraform state
* Terraform variable files containing environment-specific values
* local environment files
* database backups
* Terraform provider cache
* other local runtime artifacts

Example configuration files such as `.env.example` and `terraform.tfvars.example` document required variables without publishing active credentials.

---

## 18. Current Architecture Scope

The current version intentionally focuses on:

* Terraform-managed AWS observability
* CloudWatch monitoring
* SNS alerting
* CloudTrail auditing
* S3 audit-log protection and retention
* Docker container operations
* PostgreSQL administration
* PostgreSQL backup and recovery
* operational troubleshooting
* automated configuration validation

The project is a portfolio environment and should not be interpreted as a complete production AWS database platform.

---

## 19. Deferred Enhancements

The following capabilities are not part of the current implemented architecture and are candidates for future versions:

* VPC Flow Logs
* PostgreSQL metrics exporters
* Prometheus
* Grafana
* expanded CloudWatch metrics and alarms
* automated PostgreSQL backup scheduling
* multiple Terraform environments
* remote Terraform state
* Terraform plan/apply deployment workflows
* additional CI security scanning
* ECS-based container deployment
* managed Amazon RDS PostgreSQL integration

VPC Flow Logs are specifically deferred and should not be represented as currently implemented.
